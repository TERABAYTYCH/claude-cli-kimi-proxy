# Замер эффективности прокси

Сравнивает расход токенов на **одну и ту же работу**, выполненную двумя путями:

- **A — напрямую:** Claude Code работает с проектом сам;
- **B — через прокси:** Kimi получает задачу, а планирование делегирует Claude
  через `claude-max-api-proxy`, инструменты исполняет у себя.

## Почему сравнение честное

Оба пути заканчиваются в одном и том же Anthropic API и оба оставляют
транскрипт в `~/.claude/projects/-root-work-claude-max-api-proxy/*.jsonl` с
одинаковыми полями usage. Значит применима одна формула:

```
effective = cache_creation × 1.25 + cache_read × 0.10 + input
```

`output` считается отдельно и в эффективные input-токены не входит — он
одинаков по природе на обеих сторонах и лимит расходует иначе.

## Что меряем, а что нет

Меряем цену доставки **одинакового результата**. В неё честно входит разница
стартовых условий: у прямого пути свой системный промпт и свои определения
инструментов, у прокси — системник Kimi плюс наша карта делегирования. Это не
искажение замера, это и есть предмет сравнения.

Не меряем: скорость, качество ответа, удобство. Только токены.

## Подготовка

1. Рабочее дерево чистое: `git status` → `nothing to commit`.
2. Сервер прокси поднят из собранного кода, не под `tsx watch`:
   ```bash
   cd /root/work/claude-max-api-proxy && npm run build && npm start
   ```
3. Зафиксируй commit: `git rev-parse --short HEAD`. Сравнивать между собой
   можно только прогоны на одном commit — `TASK.md` читает исходники и выводит
   `git log`, так что при изменении репозитория меняется объём работы. Если с
   момента прошлого замера были коммиты, прямой путь надо перемерить тоже.
4. Замер запускай **сразу после прогона**: `measure.py` пишет в шапку текущий
   HEAD, а не тот, что был во время прогона.
5. Во время обоих прогонов **файлы проекта не менять** — иначе стороны прочитают
   разное, и сравнивать будет нечего.
6. Модель на обеих сторонах одна и та же: `claude-sonnet-5`.

---

## Прогон A — напрямую

1. Засеки время:
   ```bash
   date -u +%Y-%m-%dT%H:%M:%SZ    # это A_START
   ```
2. Открой **новую** сессию Claude Code в каталоге проекта.
3. Вставь в неё содержимое `TASK.md` целиком, одним сообщением.
4. Дождись финального отчёта.
5. Засеки время: `date -u +%Y-%m-%dT%H:%M:%SZ` → `A_END`.
6. Запиши `session_id` этой сессии — он понадобится, чтобы исключить из
   прогона B транскрипт того самого чата, из которого ты будешь мерить.

## Прогон B — через прокси

1. Подожди минуту после `A_END`, чтобы окна не слиплись.
2. Засеки `B_START`.
3. Открой **новый** чат в Kimi web, модель `claude-sonnet-5`, delegate-режим.
4. Вставь в него содержимое `TASK.md` целиком, одним сообщением.
5. Дождись финального отчёта.
6. Засеки `B_END`.

---

## Замер

```bash
cd /root/work/claude-max-api-proxy

python3 tests/benchmark/measure.py --label "A: напрямую" \
  --since $A_START --until $A_END

python3 tests/benchmark/measure.py --label "B: через прокси" \
  --since $B_START --until $B_END --exclude-session <session_id из шага A.6>
```

Каждый запуск печатает таблицу по вызовам и итог. Сравнивай строку
`ИТОГО эффективных input-токенов` и `вызовов`.

Машиночитаемый вывод — флаг `--json`.

## Как читать результат

| что сравнивать | о чём говорит |
|---|---|
| итого эффективных | суммарная цена одинаковой работы |
| число вызовов к API | сколько раундов потребовал каждый путь |
| среднее на вызов | насколько дорог один шаг |
| доля `cache_read` | сколько уходит на перечитывание накопленного контекста |
| доля `cache_create` | сколько на запись нового — полезная нагрузка плюс промахи кэша |

**Ожидаемая асимметрия, которую надо держать в голове при интерпретации.**
Прямой путь может вызывать несколько инструментов в одном ходе; прокси по
условию делегирования выдаёт ровно один `<invoke>` за ход. Поэтому число
вызовов у B будет выше — это архитектурное свойство, а не дефект замера.
Сравнивать имеет смысл прежде всего итог, а не цену отдельного шага.

## Повторяемость

Прогон детерминирован настолько, насколько детерминирована модель: список
файлов, команд и поисков зафиксирован в `TASK.md`, субагенты запрещены,
структура отчёта задана. Расхождение между повторами одного и того же пути
обычно в пределах 10–15% — если хочешь строгости, прогоняй каждую сторону
дважды и бери среднее.

## Перекрёстная проверка по панели Claude

Полезно снять заодно расход по индикатору лимита в UI — он показывает, как
подписка на самом деле тарифицирует работу, и позволяет проверить сам
коэффициентный расчёт (`×1.25` за запись в кэш, `×0.10` за чтение).

Чтобы сверка что-то значила:

1. **Заглуши остальную активность аккаунта на время обоих прогонов.** Панель
   суммирует всё: другие сессии Claude Code, фоновые агенты, любые запросы с
   того же аккаунта. Если параллельно работает что-то ещё, дельта будет не о
   нашем прогоне.
2. Запиши процент **до** и **сразу после** каждого прогона — четыре числа:
   `A_before`, `A_after`, `B_before`, `B_after`.
3. Сравни: отношение `(A_after − A_before)` к `(B_after − B_before)` должно
   примерно совпасть с отношением итогов, которые посчитал `measure.py`.

Если отношения сходятся — формула эффективных токенов подтверждена, и всем
измерениям в этом репозитории можно верить. Если резко расходятся — значит
подписка взвешивает кэш иначе, чем мы полагаем, и это само по себе важный
результат: тогда все сегодняшние выводы о стоимости надо пересчитать с
исправленными коэффициентами.

Результаты складывай в [RESULTS.md](RESULTS.md).
